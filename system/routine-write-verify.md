## 왜 합쳤나 (그리고 독립성은 어떻게 지키나)

옛 구조는 ②글쓰기(07:00)와 ③검사(08:00)를 **다른 세션·더 강한 모델**로 나눠 "자기 글 옹호 편향"을 막았다. 이번에 **한 루틴·한 모델(Sonnet 5)**로 합치되, 편향은 다음으로 보완한다:

1. **검사는 "깨끗한 문맥"의 별도 패스** — 글을 쓴 뒤, **새 서브에이전트(Task)**를 띄워 검사한다. 이 검사자에겐 **초안 + 원자료(collect) + 검사 규칙만** 주고, **"왜 이렇게 썼는지(작성자 속마음)"는 넘기지 않는다.** 그러면 같은 모델이라도 **처음 보는 눈**으로 적대적 검증을 한다.
2. **기계 잠금이 대형 사고를 막는다** — posts.json 잠금(①명단 축소 ②발행글 보호 ③껍데기 초안)이 커밋을 강제 검사한다(2026-07-20 도입). 모델이 실수해도 명단 붕괴·스텁은 물리적으로 차단.
3. **최후의 방어선은 사람** — 어떤 글도 사람이 "발행해" 지시 + 승인 등록해야만 라이브로 나간다. 자동 검사는 사람 부담을 더는 1차 필터일 뿐이다.

## 대상 선별 (자동 · 사람이 안 고름)

`inbox.json`에서 아래를 **모두** 만족하는 항목:
1. **`surfaced`(수집일)가 오늘** — 그날 새로 들어온 뉴스. (전날 누락분 함께 처리 가능)
2. **`verified: true`** — 날짜·사실 검증된 것만.
3. **3탭 자료 완비** — `articleVersions`에 정리본·자세히·반응이 다 있는 항목.
4. **`postId` 없음** — 아직 글 안 쓴 것.

## 0단계 — 발행 브랜치로 강제 이동 + 잠금 활성화 (첫 동작 · 반드시)

```bash
git fetch origin
git checkout -B claude/github-upload-setup-vimtlp origin/claude/github-upload-setup-vimtlp
git config core.hooksPath githooks   # posts.json 보호 잠금 활성화(강함) — 빠뜨리지 말 것
```

(기본 브랜치가 바뀌었으면 `git ls-remote --symref origin HEAD`로 확인해 그 이름으로.) 이후 모든 커밋·push가 곧장 발행 브랜치로 간다.
`git config core.hooksPath githooks`는 **posts.json 잠금**을 켠다: 명단이 줄거나(①) 발행글이 되돌려지거나(②) 초안이 껍데기(③)면 **커밋 거부**. 안 켜도 서버측 `posts guard`가 한 번 더 잡는다.

## Part A — 글쓰기 (대상마다 반복)

1. **교차검증** — `prompts/K-crosscheck.md`로 자료(정리본·자세히·반응) 간 모순·과장·함정을 훑고 앵글·렌즈를 잡는다.
2. **초안 집필** — **규칙의 단일 진실원은 `system/writing-guide.md`**(17규칙 전체 + 문단 리듬 + 과단정 스캔). `prompts/I-synthesis-deepdive.md`는 구조 뼈대로만. 특히 12(반복)·13(압축)·14(비중)·15(진행 중 사건=주장·리스크)·16(정밀표기)·17(과단정)을 반영. 골드 스탠다드 = `drafts/microsoft-mai/v1.md`(원리만).
   - **관점** — 렌즈 ① **"그래서 나한테?"**(`system/positioning.md`)를 통과시킨다. 분석 깊이는 `system/analysis-frameworks.md`에서 2~3개 적용.
3. **자기 점검** — 저장 전 writing-guide의 **발행 전 체크리스트**를 훑고 고친다.
4. **저장** — `drafts/YYYY.MM.DD_<slug>/v1.md`.
5. **posts.json 등재** — **기존 posts.json을 읽어 `posts`에 항목 append**(절대 새로 만들지 말 것), **`stage:"작성중"`**. 필드: `id, title, date(=firstSeen), type, category, stage:"작성중", layout:"feature", readMin, author:"AI 쉽게 알려주는 집", angle, versions:[{v:"v1", date:오늘, note, path}]`. `published`는 넣지 않는다.
6. **inbox.json 연결** — 대응 수집 항목에 **`"postId":"<글 id>"`** 를 붙인다.

## Part B — 검사 (대상마다, **깨끗한 문맥의 서브에이전트로**)

> Part A로 초안 v1을 다 쓴 뒤, 글마다 **새 Task 서브에이전트**를 띄워 검사한다. 서브에이전트에 주는 것: **draft v1 + 대응 `collect/<slug>*.md` 원자료 + 아래 검사 규칙**. 주지 않는 것: 작성 과정·의도·"이건 이래서 맞다" 류. (처음 보는 검사자처럼)

검사 서브에이전트가 하는 일:
1. **과단정 스캔 (규칙 17 · 7곳)** — 초안을 원자료와 대조: ① 미출처 수치·기간·비율 ② 단정 어미(한 소스 의견을 사실처럼) ③ 감정·가치 단어 ④ 소스 없는 최상급 ⑤ 가짜 인용 ⑥ 한쪽만 싣기 ⑦ 조언·훈수 어투(지켜볼 만·~하면 좋다) → 삭제·사실화.
   - 함께: 쉬운 소식의 군더더기 비유 삭제(6), 추상 표현 구체화(7), 단 확신도 낮추는 사실은 지우지 말 것(13).
2. **정직성·리스크 (9·15)** — 모든 수치·인용·URL이 소스에 실재하나? 발표값을 "주장"으로 명시했나? 양쪽 말 실었나? 진행 중 사건은 "주장/미확정" 프레이밍인가? **🎯 환각 리스크 지도**(`checklists.md`): 벤치마크·출시일·가격·버전·인용문·논문/인물 이름·"기능 있다/없다"는 원문과 1:1 대조.
3. **정밀 표기 (16)** — 뭉뚱그린 시점 없나? 처음 나오는 이름에 한글 병기?
4. **웹 팩트 재검** — 과장/오류 의심 수치·최상급은 웹으로 재확인. 못 하면 낮추거나 "확인 못 했다".
5. **수정 적용 → v2** — 규칙 기반(사실·확신도·중립성) 수정은 직접 고쳐 `drafts/<slug>/v2.md`(v1 덮어쓰지 않음). 방향은 거의 항상 **'낮추기'**, 단 ⑥ 한쪽만은 반대 소스 1개 보강. **문체·목소리 보존**. 앵글·taste는 안 건드리고 리포트에 플래그만.
6. **검사 리포트** — `drafts/<slug>/REVIEW.md`: ⓐ 무엇을 왜 고쳤나 ⓑ 남은 리스크 ⓒ 사람 판단 사안.
7. **상태 전환** — `posts.json` 해당 글의 `versions` 맨 앞에 v2를 넣고 **`stage:"작성중" → "검수중"`**. `published`는 안 넣는다.

## 검증 게이트 (커밋 전 · 반드시)

- posts.json을 바꿨으니, 커밋하면 **pre-commit 잠금**(`validate-posts.mjs`)이 자동 검사한다. 걸리면(명단 축소·발행글 회귀·껍데기) 고치고 재커밋.
- 각 글이 **1500자 이상 본문**을 갖췄는지 확인(껍데기 잠금). 세 줄 요약만 저장 금지.

## 절대 규칙 (예외 없음)

- ❌ **`node build-seo.mjs` 실행·발행 금지.** 이 루틴의 끝은 `검수중`. 발행은 사람이 최종검토 후.
- ❌ **`stage`를 `발행`으로 올리지 않는다.**
- ❌ **하루 2편 초과 금지.**
- ❌ **posts.json을 통째로 새로 만들지 않는다 — 반드시 기존 파일을 읽어 append.** (명단 잠금이 막지만, 애초에 그러지 말 것.)
- ❌ **사실을 지어내지 않는다** — 소스에 없으면 낮추거나 "확인 못 했다".
- ✅ 초안·v2·REVIEW·posts.json·inbox.json을 **발행 브랜치로 commit & push**: `git push -u origin claude/github-upload-setup-vimtlp`. non-fast-forward면 `git pull --rebase` 후 재push.
