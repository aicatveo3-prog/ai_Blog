## 왜 별도 루틴·다른 세션인가

글을 쓴 세션이 자기 글을 검사하면 **옹호 편향**이 생긴다("내가 썼으니 맞겠지"). 그래서 검사는 **다른 세션 + 더 강한 모델(4.8) + 적대적 관점**으로 독립 실행한다. (규칙: `writing-guide.md` 17번 과단정 스캔이 이 루틴의 핵심 도구.)

## 무엇을 검사하나 — 대상

`posts.json`에서 **`stage:"작성중"`** 인 항목 전부(글쓰기 루틴이 넘긴 것). 각 항목의 최신 draft(`versions[0].path`)를 연다.

## 0단계 — 발행 브랜치로 강제 이동 (첫 동작 · 반드시)

검사를 시작하기 **전에** 발행 브랜치로 옮긴다. 자동 세션은 임시 브랜치(`claude/…-xxxx`)로 스폰되고, 거기 커밋하면 push는 돼도 대시보드(기본 브랜치 빌드)엔 안 뜬다(2026-07-16 수집 루틴 사고).
```bash
git fetch origin
git checkout -B claude/github-upload-setup-vimtlp origin/claude/github-upload-setup-vimtlp
git config core.hooksPath githooks   # posts.json 보호 잠금 활성화(강함) — 빠뜨리지 말 것
```
(기본 브랜치가 바뀌었으면 `git ls-remote --symref origin HEAD`로 확인해 그 이름으로.) 이후 모든 커밋·push가 곧장 발행 브랜치로 간다 → 별도 cherry-pick 동기화 불필요.
`git config core.hooksPath githooks`는 **posts.json 잠금**을 켠다: 발행글을 검수중으로 되돌리거나(잠금②) 명단을 줄이면(잠금①) 커밋이 거부된다. **검사 루틴이 발행글 상태를 바꾸는 건 금지**이므로 이 잠금이 그 실수를 물리적으로 막는다(2026-07-20 moonshot-kimi-k3 회귀 사고). 안 켜도 서버측 `posts guard`가 한 번 더 잡는다.

## 한 편을 검사하는 순서 (대상마다 반복)

1. **자료 재수집** — 그 글의 draft와, 대응하는 `collect/<slug>*.md`(정리본·자세히·반응) 원자료를 나란히 연다.
2. **과단정 스캔 (규칙 17)** — 초안을 소스와 대조해 **일곱 곳**을 훑는다:
   ① 미출처 수치·기간·비율 ② 단정 어미(한 소스 의견을 사실처럼) ③ 감정·가치 단어(중립 사실 각색) ④ 소스 근거 없는 최상급·강조 밀기 ⑤ 가짜 인용(요지를 대사처럼) ⑥ 한쪽만 싣기 ⑦ **조언·훈수 어투(지켜볼 만·~하면 좋다·서두를 일 아니다·좋은 뉴스지만) → 삭제·사실화, 판단은 독자 몫**.
   - 함께 볼 것: **쉬운 소식에 붙은 비유**(빵집·벚꽃식)는 군더더기라 삭제(규칙 6), **추상 표현·막연한 조언**은 '무엇이 어떻게'로 구체화(규칙 7). 단 압축이 **확신도 낮추는 사실**(합의 평가액·미공개·'주장')까지 지우지 않게 주의(규칙 13).
3. **정직성·리스크 (규칙 9·15)** — 모든 수치·인용·URL이 소스에 실재하나? 발표값을 "주장"으로 명시했나? 양쪽 말을 실었나? 진행 중 사건이면 "주장/미확정" 프레이밍인가? **발행 리스크(명예훼손·정정 요구)를 자문**한다.
   - **🎯 환각 리스크 지도 (`system/checklists.md`)** — AI가 특히 잘 지어내는 유형은 **원문과 1:1 대조**한다: **벤치마크 수치 · 출시일 · 가격 · 버전 번호 · 인용문 · 논문/인물 이름 · "이 기능 있다/없다" 판단.** 초안의 이 항목이 전부 `collect/<slug>*.md` 원자료에 실재하는지 역추적. 없으면 삭제하거나 "확인 못 했다"로.
4. **정밀 표기 (규칙 16)** — 뭉뚱그린 시점("최근·그날") 없나? 처음 나오는 이름에 한글 병기 됐나?
5. **웹 팩트 재검** — 스스로 "이거 과장/오류 아닌가?" 싶은 수치·최상급은 **웹으로 재확인**한다(규칙 9). 확인 못 하면 표현을 낮추거나 "확인 못 했다"로.
6. **수정 적용 → v2** — 위에서 걸린 것 중 **규칙 기반(사실·확신도·중립성) 수정은 직접 고쳐** `drafts/.../v2.md`로 저장한다(v1 덮어쓰지 않음). 방향은 거의 항상 **'낮추기'**(수치 정성화·단정은 귀속·감정어는 중립어·최상급 삭제·가짜 인용 풀어쓰기), 단 ⑥ 한쪽만은 **반대 소스 1개 보강('더하기')**.
   - **문체·목소리는 보존**한다. 안전하게 만든다고 밋밋하게 깎지 말 것.
   - **앵글·구성·taste 같은 판단 사안은 직접 바꾸지 말고** 리포트에 플래그만 남긴다(사람 몫).
7. **발행 게이트 3질문 (`system/checklists.md`, 뉴스 설명글용으로 적용)** — ① 독자가 원문 링크 대신 이 글을 읽을 이유가 있나(쉬운 설명·맥락·정리)? ② 6개월 뒤 읽어도 안 부끄러운가(과장·성급한 단정 점검)? ③ AI 냄새 — 도입이 일반론("AI 시대에…")으로 열지 않고, 문단 리듬이 있고, 결론이 양비론으로 도망가지 않나? *(checklists.md의 "경험 문장 3개·스크린샷 직접 캡처"는 옛 도구-리뷰 포맷용이라 뉴스 설명글엔 적용하지 않는다.)*
8. **검사 리포트** — `drafts/<slug>/REVIEW.md` 에 남긴다: ⓐ 무엇을 왜 고쳤나(항목별 한 줄) ⓑ 남은 리스크 ⓒ 사람이 판단할 사안(앵글·taste). 사람의 최종검토를 빠르게 하려는 용도.
9. **상태 전환** — `posts.json`에서 `versions` 맨 앞에 v2를 넣고, **`stage:"작성중" → "검수중"`**. `published`는 넣지 않는다.

## 절대 규칙 (예외 없음)

- ❌ **`node build-seo.mjs` 실행·발행 금지.** 검사의 끝은 `검수중`. 발행은 사람이 최종검토 후.
- ❌ **`stage`를 `발행`으로 올리지 않는다.**
- ❌ **사실을 지어내지 않는다** — 소스에 없으면 채우지 말고 낮추거나 "확인 못 했다".
- ✅ v2·REVIEW.md·posts.json을 **발행 브랜치로 commit & push** (0단계에서 이미 그 브랜치): `git push -u origin claude/github-upload-setup-vimtlp`. non-fast-forward면 `git pull --rebase` 후 재push.
- ✅ **0단계(발행 브랜치 강제 이동)를 지켰는지가 곧 동기화다.** 0단계만 지키면 커밋은 자동으로 대시보드 브랜치에 오른다(옛 cherry-pick 동기화 폐지).

## 마지막 보고

- 검사한 글 제목 + 각 글에서 **고친 핵심 몇 가지** + **남은 리스크**를 한 줄씩.
- "**N편 검수 준비됨 — 최종검토 후 발행**" 을 명확히 알린다(사람의 마지막 게이트 신호).
